# Part 6: task interactions

**Status:** Candidate; stable-identity dependency  
**Backlog:** `TL-TASK-001`  
**Verified:** 2026-08-25; [feedback intake](../../evidence/2026-08-25-home-feedback-specification-intake.md), `SwipeCompleteRow`, `UploadClient.updateActionItem`, and the action-item API route

## User problem

Completion works through the task circle and a right swipe, but task editing and task deletion do not exist. The visible note-card trash action deletes the entire parent note. Completion is currently matched by recording ID plus normalized task text, so duplicate or edited text can target the wrong task.

## Outcome

Give each task a predictable, accessible interaction set: circle or right swipe to complete/reopen, row tap to edit, and left swipe to delete only that task. Parent-note deletion remains a separate, explicitly labeled action.

## Stable identity gate

Before adding edit or delete, the server assigns every canonical to-do an immutable task ID that:

- is generated by the service, not trusted from model output;
- remains stable across fetches, action-state changes, and content edits;
- is unique within its source recording and may coexist with identical task text;
- is used by the client, API, action-item state, note revisions, and analytics mutation result; and
- never appears in analytics, user-facing copy, or tracked evidence.

Legacy records receive service-side IDs through a deterministic, idempotent compatibility migration. If a legacy task cannot be mapped unambiguously, it remains readable and opens its source, but mutations fail closed with a retryable explanation rather than changing every text match.

## Interaction contract

- **Direct circle:** the primary visible Complete/Reopen control. It keeps optimistic feedback and rolls back on server failure.
- **Right swipe:** Complete or Reopen, retaining the familiar directional behavior. The full-swipe threshold may remain, but the result and failure state must be announced.
- **Row tap:** open a focused task editor, not the entire note in read mode. The editor exposes action text plus existing optional date, priority, and context fields. It also includes explicit Save and Cancel actions and a link to the source note.
- **Left swipe:** reveal a red **Delete task** action. Disable destructive full swipe. Selecting it asks **Delete this task? The source note stays.** with Cancel and Delete task actions.
- **Undo:** after confirmed deletion, remove the row and show an accessible six-second Undo action. Undo restores the same task ID and prior fields. The mutation/revision API must support idempotent restore; it may use the existing immutable revision ledger without extending the note's retention policy.
- **Non-gesture alternatives:** expose Complete/Reopen, Edit, Open source, and Delete task through an accessibility action set and a long-press/context menu where appropriate.
- The existing parent-note trash action remains in note-card/note-detail chrome with its separate confirmation and must never be triggered from a task swipe.

## API contract

- Replace text-addressed completion for current clients with a task-ID-addressed route scoped to the source recording.
- Completion, edit, delete, and restore accept an idempotency key and the expected current note revision. A stale revision returns a conflict and the client refreshes before retrying.
- Editing changes only the targeted to-do fields and preserves its task ID, completion history, other to-dos, source note, and original model revision.
- Deletion creates a user-mutation revision for the targeted task only. Restore is idempotent and revives that same task, not a duplicate.
- Old clients remain compatible through the prior action-item route, but an ambiguous normalized-text match is rejected rather than updating multiple tasks.
- Responses and logs use bounded safe failure codes; they never echo task or note content.

## Metric and guardrails

The primary metric is a successful extracted-task revisit or completion within seven days. `action_item_toggled` remains the completion event. `task_edited`, `task_deleted`, and `task_delete_undone` may be added only after the metrics/analytics allowlist accepts bounded result and surface properties.

Guardrails are mutation failure rate, stale-revision conflict rate, ambiguous-target rejection, undo success, accidental parent-note deletion, duplicate task creation, and accessibility-action availability. Edit/delete volume is behavior evidence, not automatically a quality failure without denominator and context.

## Acceptance criteria

- Server tests cover stable ID creation/preservation, duplicate text in one and multiple notes, legacy unambiguous and ambiguous mappings, completion, edit, delete, restore, idempotency, stale revisions, authorization, owner isolation, safe failures, and parent-note preservation.
- Client tests cover direct circle, both swipe directions, destructive full-swipe prevention, edit save/cancel, delete confirmation, six-second Undo, offline rollback, refresh conflict, repeated taps, app backgrounding, and source navigation.
- Accessibility tests prove every gesture has a labeled alternative and focus moves predictably after completion, deletion, undo, and error.
- Privacy tests prove no task content or identifier enters analytics, errors, release evidence, or logs.

## Non-goals, authority, and rollback

This part does not add bulk editing, drag ordering, recurrence, reminders, parent-note deletion from a task, agent write actions, or model/schema changes. Mike approves the interaction design; routine reversible implementation proceeds inside the selected slice. Any agent write scope remains separately approval-gated.

Rollback hides edit/delete gestures and returns current clients to completion-only behavior while the additive stable IDs and immutable revisions remain compatible. The release manifest records source commit, migration/API identity, compatibility route, test/canary outcomes, internal build, and rollback target without task content or identifiers.
